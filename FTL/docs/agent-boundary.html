The agentic loop

The other model job, and the only self-extending thing in the app: it teaches itself to read senders nobody wrote a parser for. It is a cycle, and it closes through you.

Why the loop has to close through you. The verifier needs an oracle — held-out mail with a known-good answer. That exists only where a hand-written parser already covers the sender, which is exactly where the learned pattern is redundant. On a mailbox nobody has written a parser for, attempted == 0 for every sender and a pattern that is 100% correct still only ever reaches provisional. The queue is the one oracle such a mailbox generates on its own, because you look at every row anyway.

Edge cases — what happens when the agent can't answer

The boundary is easiest to see where things go wrong. In every row below the failure is absorbed by deterministic code or handed to a person; none of them ends in a guess reaching the ledger.

Refused before the model sees it, and the row is flagged, never dropped. Measured: this refuses 36% of money mail — a hard ceiling on how much of the queue the tagger can reach.

Remaining rows stay untagged and say so. They are picked up by the memory-only refresh on the next queue load, or by the next sync — never by spending more calls.

The tagger is dropped from the rail entirely. 8 calls × 3.82s is the whole budget; spending it there would mean rows parsed and never written.

The loop starts. Discovery notices, synthesis proposes, the verifier scores — and on a mailbox with no oracle the result is provisional no matter how good it is.
